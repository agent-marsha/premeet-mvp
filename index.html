    Security model applied in this prototype

    This client holds no credential of any kind. Inference, the credit ledger, and the OpenRouter sub-keys all live server-side — which is why live generation is not wired into this static page. The controls below are implemented in-browser here to demonstrate behaviour.

    L7

    Detection & kill switch

    Alerts on spend rate and per-user COGS; a one-button halt that stops new enqueues.

    L6

    Secret management

    Keys in a managed store, rotated, never logged, never shipped to the client. CI secret scanning.

    L5

    OpenRouter controls

    Per-tenant sub-keys with hard credit limits + model allowlist; a global account spend cap.

    L4

    Job sandbox

    Fixed pipeline, hard step/token/page budgets, SSRF guards, injected web content treated as data.

    L3

    Credit ledger

    Prepaid, reserve-then-settle, never negative, idempotent, reconciled daily.

    L2

    API abuse defenses

    Server-side authorization, rate limits, concurrency caps, idempotency, subject dedupe.

    L1

    Account & identity

    Email verification, bot detection, card-on-file to unlock free credits, velocity limits.

    —

    Why not client-side?

    A browser-held OpenRouter key is exactly the unbounded-loss scenario the plan forbids: it can be read from the bundle and spent directly.

    PreMeet MVP prototype · the browser-side ledger and limits are illustrative. Backend (worker + ledger + per-tenant OpenRouter sub-keys) is the next deploy — it cannot host on GitHub Pages because Pages is static-only and must never hold the key.
